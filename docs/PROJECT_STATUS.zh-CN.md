## 1. 项目目标

以 Skyward 上游为基础，先完成不破坏原有功能的主题扩展，再把 Xiaomi 15 Pro（`haotian`）专项分支中可复用的能力，经过设备差异分析后移植到 Xiaomi 17 Pro Max（`popsicle`），最终交付可在 popsicle 真机启动、操作、解密、刷写和更新的独立 Recovery。

项目原则：

- **先完成主题，再推进 popsicle 设备适配。** 主题工作不能因为设备移植而被跳过。
- **主题是附加外观，不是功能替换。** 原版浅色、深色主题和现有页面、操作、布局、交互必须保留；新主题由用户主动选择。
- **设备能力以 popsicle 自身固件、内核、设备树和分区表为准。** 不把 haotian 的硬件参数、驱动、固件、服务启动顺序直接复制过来。
- **安全相关操作默认保守。** AVB、分区写入、密钥服务等功能必须保留明确提示、用户控制和失败保护。
- **完成标准以可复现构建和真机测试为准。** 没有测试记录的功能不得标记为“真机已验证”。

**主题验收条件**

1. 原版主题仍可正常选择和使用，视觉与交互没有被新主题破坏。
2. 用户能主动切换主题，选择可持久化；不存在只做了样式却没有入口的情况。
3. 所有主要页面和弹层均有适配，不出现文字裁切、控件错位、危险状态不清晰。
4. 主题只改变外观，不移除、隐藏或替换原有 Recovery 功能。
5. 完成构建与回归测试后，才将主题标记为已完成。

- 🟡 核实 popsicle 的 stock recovery、系统版本、分区布局、内核模块、固件和运行时服务。
- 🟡 分析 popsicle 的 NXP Weaver、Gatekeeper、OMAPI/eSE 服务启动依赖及解密流程。

### 阶段 A：主题体系完善

- 原版主题与新主题并存，用户可选、可持久化。
- 统一主题 Token、颜色角色、字体、圆角、间距、动效和材质规范。

- 在不改变功能的前提下，探索更多 Material You / Material 3 Expressive 视觉方案。

### 阶段 B：popsicle 正式适配

- 先完成可启动、可操作的基础 Recovery。
- 再完成 Data 解密和关键分区操作。
- 最后完成高级硬件能力、OTA、更新和自动化测试。
- 为 popsicle 单独维护设备配置、构建产物和发布说明。

### 阶段 C：设备适配框架

- 把设备差异集中到设备配置、服务清单、固件映射和能力声明中。
- 区分通用功能、SoC 家族功能和单设备专属功能。
- 为设备能力建立自动检测与降级机制，避免不支持的硬件功能导致 Recovery 启动失败。
- 建立设备适配模板、测试清单和维护文档，降低后续移植成本。

### 阶段 D：更多设备

候选探索方向（均未承诺支持，也不代表已有可用构建）：

- Google Pixel：Pixel 1、Pixel 2、Pixel 7 等。
- Xiaomi：Redmi K20 Pro、MIX 2S、Redmi Note 7 等。
- 其他具备可获取 stock recovery、内核、设备树和必要固件的 Android 设备。

设备支持必须逐台确认启动链、分区布局、内核 ABI、驱动、加密实现和固件许可条件；不能仅凭 SoC 相同或设备树相似就宣称兼容。

### 阶段 E：长期功能拓展

- 更完善的备份/恢复策略和任务队列。
- 更清晰的刷机前检查、风险提示与失败恢复。
- 设备能力检测、日志导出和诊断报告。
- 可选插件式扩展能力，但核心 Recovery 功能保持精简、可靠。
- 多设备构建矩阵、自动化回归测试和稳定更新通道。

## 7. 当前执行顺序

1. **先完成 M3E + Liquid Glass 主题。** 补齐主题选择、持久化、页面适配和回归测试。
2. **主题验收后冻结主题基线。** 确保原版 UI 与 Recovery 功能不受影响。
3. **建立 popsicle 设备配置。** 先做最小启动适配，不急于加入所有高级功能。
4. **优先打通 Data 解密。** 以 popsicle 的 Weaver + Gatekeeper 实际链路为核心。
5. **逐项移植 haotian 的可复用能力。** 每项先分析、再实现、再验证。
6. **完成真机回归和独立发布。** 没有真机记录的项目保持“待验证”。
